# Server 2: ML Compute Engine Architecture

Server 2 serves as the heavy-lifting Machine Learning pipeline for the OmniVision microservices architecture. It receives raw images over the local network (from Server 1), processes them sequentially through multiple AI models, and returns a multimodal (text and audio) response.

## Technical Stack
- **Framework**: FastAPI (Python) running on Uvicorn.
- **Object Detection**: YOLOv8 (`yolov8n.pt`) via the `ultralytics` package.
- **Vision LLM**: LLaVA (`llava:v1.6`) served locally via Ollama.
- **Text-to-Speech**: Piper TTS (`en_US-lessac-low.onnx`) running via high-speed CLI subprocesses.

---

## The Network Flow

### 1. Inbound Connection
Server 2 runs a FastAPI application bound to `0.0.0.0:8001`. 
By default, development servers bind to `127.0.0.1` (localhost), which actively rejects traffic from other computers. By binding to `0.0.0.0`, Server 2 listens on all available network interfaces, allowing Server 1 (e.g., `192.168.0.140`) to connect over the local Wi-Fi.

Additionally, a **CORS (Cross-Origin Resource Sharing)** Middleware is injected into the FastAPI app to explicitly whitelist traffic originating from Server 1, preventing browser-level or gateway-level security blocks.

### 2. The API Endpoint (`POST /internal/full-pipeline`)
The server exposes a single internal REST endpoint. 
It expects a `multipart/form-data` payload containing an image file. This format is crucial because it allows the safe transmission of binary image data over HTTP without massive base64 encoding overheads during the initial hop.

---

## The AI Processing Pipeline

When an image hits the endpoint, it is temporarily saved to the local disk and passed through three stages:

### Stage 1: Spatial Awareness (YOLOv8)
The image is passed into a Nano YOLOv8 model (`yolov8n.pt`). 
- **Why**: Vision LLMs like LLaVA are great at describing scenes but sometimes hallucinate small objects or miss specific spatial details. YOLOv8 acts as a highly accurate, deterministic "ground truth" extractor.
- **Technical Detail**: The bounding box classifications are extracted and flattened into a deduplicated list of strings (e.g., `["person", "car", "stop sign"]`).

### Stage 2: Scene Understanding (Ollama + LLaVA)
The original image, alongside the extracted YOLOv8 object list, is sent to Ollama.
- **Ollama Networking**: The Ollama background service is configured with `$env:OLLAMA_HOST="0.0.0.0"` to ensure it isn't rejecting internal requests. The FastAPI server interacts with it via the `ollama` Python client over port `11434`.
- **Context Injection**: The prompt specifically injects the YOLOv8 detections: *"The following objects were detected... Please explicitly include this context"*. This forces the LLM to ground its visual description using the deterministic data from Stage 1, dramatically reducing hallucinations.

### Stage 3: Audio Synthesis (Piper TTS)
The text description generated by LLaVA is piped into Piper TTS.
- **Why Piper**: Traditional TTS engines like Coqui or Bark are extremely heavy and slow. Piper is highly optimized for local CPU/edge inference.
- **Technical Detail**: Instead of using a complex Python wrapper, `main.py` uses Python's `subprocess.Popen` to call the compiled `piper` binary directly. The text is passed into Piper's `stdin`, and Piper renders it into a `.wav` file on disk. This is the fastest possible execution path.

---

## Outbound Response & Cleanup

Once the `.wav` file is generated:
1. The `.wav` file is read and encoded into a **Base64 string**.
2. Both the temporary image and temporary audio files are forcefully deleted from the disk to prevent storage bloat.
3. The server returns a strict JSON payload back to Server 1:
```json
{
  "description": "A red car is parked next to a stop sign...",
  "audio_base64": "UklGRiQAAABXQVZFZm10IBAAAAABAAEAQB8AAEAfAAABAAgAZGF...",
  "detected_objects": ["car", "stop sign"]
}
```

## Testing the Pipeline

A local test script (`test_pipeline.py`) is provided. It mimics Server 1 by automatically generating a red 100x100 pixel image, dispatching it to the pipeline via multipart HTTP, and decoding the resulting Base64 audio back into a playable `.wav` file.
